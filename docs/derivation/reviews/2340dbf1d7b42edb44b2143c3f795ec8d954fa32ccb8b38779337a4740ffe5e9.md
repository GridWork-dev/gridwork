### The gate change, read adversarially

Because this change edits the marker checker being used to check it, I did not rely on
the seeds already in CI or on the commit messages' claims about them. I wrote 20
marker-check probes of my own (a 17-case battery plus 3 controls) and ran them against
`--markers` in a throwaway clone.

The honest answer to "can the new form silence the marker requirement on a file that
DOES derive something" is **yes, mechanically — and the change says so in four places
rather than hiding it.** `owes_marker()` keys on file extension, so the gate is
content-blind by construction; CLEANROOM.md, this directory's README, and the gate's own
comment block all state that the gate proves a claim was MADE and attributable, never
that it is true, and the README amendment explicitly raises a `none` to *more* scrutiny
than a citation. That is the correct disposition of an unfalsifiable-by-machine claim,
and it is why check 1 above was done by reading the crate rather than by reading the
syntax.

What I could verify is whether the constraints the docs advertise are **enforced or
merely written down**. All four are enforced:

- a bare `Derivation: none`, with or without trailing whitespace, is rejected — the file
  reads as unmarked, exactly as claimed, because `cited_ids`' trailing `[^[:space:]]`
  never matches it (2 probes);
- `none` beside a real citation is rejected in **both** orders, not just the one CI
  seeds (2 probes);
- near-miss spellings fail **closed**: `NONE` and `none.` are treated as ordinary
  citation IDs, resolve in neither registry, and are rejected (2 probes);
- a `none` inside a string literal does not count as a marker (1 probe).

I also checked the one line of the `--subject` change that this change's own digest run
never exercises — the `[[ "$id" == "$NONE_ID" ]] && continue` skip — because if `set -e`
fired on its false branch, every digest citing a real source would silently lose its
registry rows. It does not: I hand-recomputed the digest for an unrelated gated file
carrying three real citations (`CAP-002`, `ECMA-48`, `POSIX-WINSIZE`), folding all three
rows in myself, and got `a3109da71038a5c74bdd9eec798faf43d375550a4472c9d6e0d93b45482b912e`
— identical to the gate's. The skip's other claim holds too: altering **only** the
`none` reason text and nothing else moved the subject from `2340dbf1…` to `f0c64b3f…`,
so the declaration's wording is inside the reviewed surface and re-opens review, which
is what makes a `none` reviewable at all.

Two bounded observations, neither a blocker and neither a regression:

1. The mandatory "reason" is enforced as *one non-whitespace token*, so
   `// Derivation: none —` with an em-dash and nothing after it passes. This is not new
   and not specific to the declaration form: `// Derivation: ECMA-48 —` passes
   identically, and always has — the new form inherits `cited_ids`' existing description
   rule rather than loosening it. Verified both directions.
2. The "never both" check sees only the comment forms `cited_ids` recognizes (`//` and
   `#` at line start). A citation written as a `//!` doc comment or a `/* */` block
   comment sitting beside a `//` `none` passes as "declares no derivation". Worth naming
   because `//!` is the idiomatic Rust module-doc form and this is a Rust repo — but the
   honest-mistake path is unchanged: either of those forms **alone** still fails closed
   as unmarked, which I confirmed, so no author reaches this state by accident. Reaching
   it requires deliberately writing a false `none` next to a citation in an unrecognized
   comment form, which is the same lie as a bare false `none` on a deriving file, and
   lands on the same reader. Recorded so the next round does not re-derive it.
