## Notes

### citations — now correct, verified against the specification rather than the fix note

`crates/gwk-pty/src/lib.rs:86` reads:

```
// Derivation: ECMA-48 §8.3.20 — CUF moves the active position forward by
// Pn columns, with parameter default Pn = 1.
```

Checked against ECMA-48 5th edition (June 1991) itself, obtained from the `Where` column
of the registry row that the marker cites. §8.3.20 reads verbatim:

```
8.3.20   CUF - CURSOR RIGHT
         Notation: (Pn)
         Representation: CSI Pn 04/03
         Parameter default value: Pn = 1
         CUF causes the active presentation position to be moved rightwards in the
         presentation component by n character positions if the character path is
         horizontal, or by n line positions if the character path is vertical, where n
         equals the value of Pn.
```

Both halves of the marker are what that section says. `04/03` is `0x43` = `C`, the final
byte the test actually emits. "Forward by Pn columns" is the horizontal-character-path
case, which is the one the test exercises; the marker does not claim to restate the
vertical branch and does not need to.

The behavior was verified, not assumed. `cargo test -p gwk-pty --locked --offline` passes
from this worktree: `hello\x1b[5C world` lands the cursor at column 16, and `a\x1b[Cb`
lands it at column 3 — the parameterized advance and the omitted-parameter default of 1,
which is what §8.3.20 specifies.

One improvement beyond the section number, worth recording because it was not what was
asked for. The previous marker justified the default as "a CSI sequence with no parameter
defaults Pn to 1", which overgeneralizes: ECMA-48 sets defaults per control function, not
per sequence type, and plenty are 0 — §8.3.117 SGR is "Parameter default value: Ps = 0",
§8.3.39 ED likewise. The revised wording, "with parameter default Pn = 1", is scoped to
CUF and matches the spec's own line. The rewrite fixed a second, quieter inaccuracy.

**Marker placement.** All VT behavior is delegated to the dependency, so the only
non-obvious terminal behavior this change asserts anywhere is in the test, and the marker
sits directly above it. Re-checked the rest of the gated set for behavior that should
carry a marker and does not: `DEFAULT_SCROLLBACK` is a retention policy no spec sets;
the zero-dimension refusal is the dependency's documented `Options` contract, not a
terminal control function; `write`'s byte-slice signature states a parser contract this
crate does not implement. No citation gap.

**Root cause fix, `CLEANROOM.md` rule 3.** The illustrative marker now reads
`§8.3.20 — CUF advances the active position by Pn, default 1`, which is correct. The
block also now records what the old example got wrong and why it mattered. I checked
those claims too rather than accepting them: §8.3.14 is indeed `CPR - ACTIVE POSITION
REPORT` (`CSI Pn1;Pn2 05/02`), a report solicited by DSR or sent unsolicited that moves
nothing; and ECMA-48 defines no cursor save/restore control function anywhere in §8.3 —
a search of the full text returns none, and DECSC/DECRC are DEC private, which is why
routing them to `XTERM-CTLSEQS` is the right pointer. The correction is accurate in both
of its historical claims, which matters here more than usual: this block is what the next
marker gets copied from.

### Outside this record's verdict — one new finding in a non-gated file

`tools/no-network.sh` is not under a gated prefix, so it does not bear on the four checks
above. Flagging it because it is new in this change and it does not work in the
environment it was added for.

The CI step exports `GHOSTTY_SOURCE_DIR` and `GHOSTTY_ZIG_SYSTEM_DIR` via
`eval "$(./tools/pty-toolchain.sh --env)"`, then invokes `./tools/no-network.sh` to run
cargo inside the namespace. The `unshare -rn` path inherits those exports. The
`sudo -n unshare -n runuser -u … -p` fallback does not: `sudo` applies `env_reset` before
`runuser -p` ever sees the environment, so `-p` preserves what sudo left, not what the
caller exported. Tested directly rather than reasoned about — with `PROBE_VAR=hello`
exported, the `unshare -rn` path prints `PROBE_VAR=[hello]` and the sudo path prints
`PROBE_VAR=[]`.

That fallback exists specifically because hosted runners refuse `unshare -rn`, so on a
hosted runner the `pty` job takes the path that drops both variables. With
`GHOSTTY_SOURCE_DIR` unset, `libghostty-vt-sys` clones ghostty during the build — the
behavior `README.md:23` and `src/lib.rs:19-21` both call out — inside a namespace with no
network. It fails rather than passing falsely, so the script's central safety property
holds and no false proof is produced; but the job goes red on exactly the runners the
fallback was written to support.

The header comment at `tools/no-network.sh:38-39` also claims `-p` "keeps the
environment", which the probe above contradicts for exported variables. `HOME` happened to
survive on this box, so the sentence is not uniformly wrong, but it describes a guarantee
the code does not deliver.

Smallest fix that works on both paths, without sudo env flags or naming the variables
twice: move the `eval` inside the sandbox —
`./tools/no-network.sh bash -c 'eval "$(./tools/pty-toolchain.sh --env)"; cargo …'`.
`--env` only prints exports and does no work, so it is safe to run with no network.
