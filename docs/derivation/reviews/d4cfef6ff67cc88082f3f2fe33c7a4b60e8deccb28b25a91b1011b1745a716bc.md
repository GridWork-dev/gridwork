### Required finding — `check_captures()`'s hash lookup is not cell-anchored (demonstrated, two ways)

This is the headline finding and it lives in `tools/cleanroom-gate.sh`, not in the
gated crate — it does not un-tick any of the four boxes above (the 16 markers in
`crates/gwk-pty` all resolve through the *other* lookup, `resolves()`, which I verified
*is* cell-anchored and is not affected — see the control test below). I'm putting it
first because it's more load-bearing than anything in the boxes.

`check_captures()` (`tools/cleanroom-gate.sh:182-217`) hashes every file under
`docs/derivation/captures/` and checks it against the registry with:

```bash
if ! grep -qE "^\|.*${sum}.*\|" "$reg"; then
```

This only requires that the line **start** with `|` and contain a later `|` somewhere
after the hash — it does not anchor the hash to the registry's own hash *column*. I ran
two live exploits against the real gate in this worktree (both cleaned up immediately
after; `git status --porcelain` was empty before, during isolation, and after — see
commands below):

1. **Hash cited only in prose, not in the hash cell.** Created an unregistered file
   under `docs/derivation/captures/`, computed its real sha256, and appended a row to
   `CAPTURES.md` whose *hash column* was a harmless placeholder (`0000…0000`) but whose
   *description column* happened to mention the real hash in a sentence ("…the value
   `<sum>` showed up once in a debugging session and is quoted here purely as prose…").
   `: | ./tools/cleanroom-gate.sh` → `cleanroom-gate: clean`, exit 0. **Accepted.**
2. **Hash as a substring of a padded/corrupted hash cell.** Same setup, but this time the
   registry row's hash cell itself was `aaaa<sum>bbbb` — a corrupted value that merely
   *contains* the real digest. Same result: accepted, exit 0.

Both were reverted with `rm -f` + `git checkout -- docs/derivation/CAPTURES.md`;
`git status --porcelain` confirmed clean before moving on.

As a control, I ran the same shape of attack against the *other* lookup in the same
file — `resolves()`, used by `check_markers()` to resolve a `Derivation: ID` citation —
by adding a fake ID to `SPECS.md` in prose only and citing it from a seeded gated
source file. That one was correctly rejected (`cleanroom-gate: … cites
'FAKE-PROSE-ID', which is in neither CAPTURES.md nor SPECS.md`), because `resolves()`
anchors to the cell: `^\|[[:space:]]*\`?${id}\`?[[:space:]]*\|`. `check_captures()`'s
`sum` lookup has no equivalent anchor. The design is known to matter — `resolves()`'s
own comment says "Table-cell match, so a passing mention in prose does not register an
ID" — it just wasn't applied to the sibling function that does the same kind of lookup
for hashes.

Why this matters: `CAPTURES.md` states as its whole reason for existing that
`cleanroom-gate` "verifies that every file under that directory … hashes to something a
row carries. Edit the bytes and the gate rejects the change." That's the claim I tested,
and for a crafted registry it's false — a corrupted or dishonestly-described row can
validate a capture file's bytes without the file's hash ever occupying the row's actual
hash field. This is the same bug *class* every round has found (a document asserting
something the code does not do), just relocated from a source comment into the gate's
own regex versus its own accompanying prose.

I'd suggest anchoring the same way `resolves()` does (something like
`^\|[^|]*\|[[:space:]]*\`?${sum}\`?[[:space:]]*\|`, matching the second cell
specifically) — but that's your call to make, not mine to land.

### BE HARDEST #2 — `! -type d` vs `-type f`, and what the `-f` guard actually does

Both hold, and I ran the comparison rather than trusting the comment:

```
$ find docs/derivation/captures -type f -name 'via-symlink.txt'   # (empty — misses it)
$ find docs/derivation/captures ! -type d -name 'via-symlink.txt'
docs/derivation/captures/via-symlink.txt
```

`find -type f` reports the type of the symlink *itself* (`l`), not its target, by
default (no `-L`), so it would have silently skipped a symlink pointing at a real
unregistered file — exactly the gap the comment claims `! -type d` avoids. `! -type d`
picks it up, and the subsequent `[[ -f "$f" ]]` (which *does* dereference, being a bash
conditional stat rather than `find`'s lstat) correctly follows it through to the real
target and hashes it — the gate rejected that unregistered symlink target with a normal
"is not registered" message, not a skip. So: the comment's claim is true, verified by
running the counterfactual, not by reading it.

## Ruling requested: is the subject digest's gated-files-only scope a real hole?

Short answer: **yes, it's real, and I could reproduce the shape of it without touching
anything** — but I don't think folding the whole of `SPECS.md`/`CAPTURES.md` into every
subject is the right-sized fix, for the reason you already suspect.

**Why it's real.** The subject is computed only from paths matching
`.github/cleanroom-paths.txt` (`crates/gwk-pty`, `crates/gwk-adapter-`,
`crates/gwk-tui/src/workspace/`). `SPECS.md` and `CAPTURES.md` match none of those
prefixes. So: a future PR that edits *only* `docs/derivation/CAPTURES.md` — say,
rewriting CAP-002's "What it observably shows" column to describe something the
capture doesn't actually show, or adding a new row with a fabricated description — has
an empty `touched` set in the `cleanroom-gate` job. `check_captures()` still runs
unconditionally, but it only checks that a *file under `docs/derivation/captures/`*
hashes to *some* row; it says nothing about whether that row's prose is honest. And
because the job's gate for "does this PR need a second-reader record" is driven by the
same `touched` set, a registry-only PR needs none. This PR's own review record — this
file — asserts the citations are TRUE as of *right now*; nothing stops a later,
unrelated PR from quietly rewriting what a citation this review vouched for actually
means, without ever re-opening review, and without this record's subject ever
reflecting that the thing it attested to has moved. I didn't need to simulate this one
in the repo to be confident it's real — it follows directly from reading
`cleanroom-paths.txt` against the subject computation in `tools/cleanroom-gate.sh:251-271`,
and from the empty-`touched` fast path at the top of the same file (`tools/cleanroom-gate.sh:234-244`),
which I did read carefully rather than skim.

**Why I'd stop short of "hash the whole registries into every subject."** `CAPTURES.md`
is explicit that pre-seeding rows ahead of the code that will cite them is meant to be
cheap: "A row nothing cites costs nothing; a missing row blocks a PR." If the subject
unconditionally folded in the full byte-for-byte content of both registry files, then
*any* future registry edit — adding `CAP-050` for a totally unrelated crate, fixing a
typo in a description nobody's citing yet — would change the subject computed for
*every* PR that also happens to touch a gated crate path around the same time, forcing
a fresh review even when nothing about what that PR's markers actually cite has moved.
That's the "every registry edit forces a fresh round" failure mode you flagged, and I
think it's a real cost, not a hypothetical one — it directly fights the stated design
goal of keeping row pre-seeding cheap.

**What I'd suggest instead, without touching it myself:** narrow the fix to what a
given review actually vouches for — the *specific registry rows* that the reviewed
diff's `Derivation:` markers cite — rather than the registries' entire contents. Fold
into the subject not "the blob hash of `CAPTURES.md`" but "the text of the specific
rows whose IDs appear in a `Derivation:` marker somewhere in `touched`" (extractable
with the same `resolves()`-style cell match already in the file). That closes exactly
the hole I demonstrated the shape of — silently rewriting a row a past review vouched
for — without punishing an unrelated pre-seed or a typo fix in a row nothing yet cites.
It's more code than a blanket "add two more paths to `cleanroom-paths.txt`," and it's
your call whether that complexity is worth it versus, say, treating a cited row as
append-only/immutable-once-cited (a different mechanism entirely, enforced as a diff
constraint rather than a digest one) — I'd want to hear your read on which failure mode
you'd rather live with before I'd commit to either.
