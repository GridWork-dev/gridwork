### FINDING 1 — `POSIX-TERM §11` does not contain any of the three facts cited against it

`SPECS.md` defines `POSIX-TERM` as *"POSIX.1-2024 §11 General Terminal Interface"*. That
is XBD Chapter 11. Three markers cite it:

- `src/session.rs:111` — SIGWINCH delivery on window-size change
- `src/record.rs:55` — window size is set by `tcsetwinsize`, not carried in written data
- `src/attach.rs:69` — same claim, for replay

XBD Chapter 11 was fetched and searched exhaustively. It contains:

| term | occurrences in XBD §11 |
|---|---|
| `SIGWINCH` | **0** |
| `window size` | **0** |
| `winsize` / `ws_col` / `ws_row` | **0** (one incidental `tcsetwinsize` only) |
| `tcgetwinsize` | **0** |
| `tcsetwinsize` | 1 |

The single hit is a parenthetical list about background-write access control:

> "…TOSTOP is ignored; that is, the effect is identical to that of terminal writes when
> TOSTOP is set (see 11.2.5 Local Modes, *tcdrain*(), *tcflow*(), *tcflush*(),
> *tcsendbreak*(), *tcsetattr*(), *tcsetpgrp*(), and *tcsetwinsize*())."

That mentions the function's name in a SIGTTOU context. It defines no window-size
semantics and never mentions SIGWINCH. All three facts live in XSH, on the
`tcsetwinsize()` function page — a different volume of the standard, outside the ID's own
declared scope.

This is structurally the failure CLEANROOM.md rule 3 documents in its own worked example
("§8.3.14 is CPR, a device *report* that moves nothing"): the right document, the wrong
section, resolving happily through the gate.

**Fix pattern** — either broaden the registry row to `POSIX.1-2024` and cite the function
page (`POSIX-TERM XSH tcsetwinsize`), or keep §11 scoped as-is and add a second registry
row for the XSH function pages. Do not leave §11 on facts it does not carry.

### FINDING 2 — the SIGWINCH condition in `src/session.rs` is stated as the standard's opposite

`src/session.rs:111-114`:

```
// Derivation: POSIX-TERM §11 — setting the window size through the terminal
// interface delivers SIGWINCH to the foreground process group on success.
// That signal is the child's cue to re-read the size and repaint, so the
// second line below is a commitment: once it runs, the child has been told.
```

POSIX.1-2024, `tcsetwinsize()`, DESCRIPTION — normative:

> "If the terminal size **was changed** successfully, a SIGWINCH shall be delivered to the
> foreground process group associated with the terminal. **No signal shall be delivered if
> the terminal size was changed to the same value it had before the `tcsetwinsize()`
> call.** A SIGWINCH may also be delivered to an implementation-defined set of other
> processes."

The condition is **a change**, not **success**. A `tcsetwinsize()` that sets the size to
the value it already held *succeeds* — RETURN VALUE gives 0 — and the standard states in
a separate sentence that no signal is delivered. The marker's "on success" names exactly
the case the standard carves out.

The claim that rests on it does not hold either. `Session::resize(80, 24)` on a PTY
already at 80×24 completes, returns `Ok(())`, and delivers nothing; "once it runs, the
child has been told" is false there. The consequence is benign — nothing changed, so
nothing needs repainting — but the cited source does not say what the marker says it
says, which is the check.

Two smaller inaccuracies in the same marker: it omits the "may also be delivered to an
implementation-defined set of other processes" clause, and it does not note that
`tcsetwinsize()` from a background process group can raise SIGTTOU or fail with `[EIO]`
instead.

**Fix pattern** — "delivers SIGWINCH to the foreground process group **when the size
actually changes**; a call that sets the size to its current value succeeds and delivers
nothing."

The mechanism half of the marker is correct and was verified down to the syscall:
`Pty::resize` → `pty_process::sys::set_term_size` → `rustix::termios::tcsetwinsize`. The
markers at `record.rs:55` and `attach.rs:69` are also **substantively true** and in fact
better supported than they claim — the same page states normatively that *"No actions
defined by this volume of POSIX.1-2024, other than a call to `tcsetwinsize()`, a close of
the last file descriptor…, or an open of the first file descriptor…, shall cause the
terminal window size to change,"* which is a stronger guarantee than "not carried in the
data a process writes." Only their section is wrong (Finding 1).

### The `resize` ordering argument — checked against the code, not the comment

Asked for adversarially, so reported in full.

**The stated reason is the real reason.** `session.rs:124-130` calls `self.grid.resize(…)`
first, propagates with `?`, and only then `self.pty.resize(…)`. `Grid::resize`
(`lib.rs:117-122`) guards `cols == 0 || rows == 0` and returns `None` before touching
libghostty-vt, so it is pure validation with no state change on the failing path.
Validate-then-commit is what the ordering achieves, and it is enforced rather than
asserted: `a_refused_resize_does_not_reach_the_child` reads the size back with
`rustix::termios::tcgetwinsize` — the kernel, not the crate's own bookkeeping — and
requires 80×24 after a refused `resize(0, 24)`. That test passes.

**The negative claim is sound.** "`pump` and `resize` both take `&mut self` and `resize`
has no await point, so a repaint cannot land mid-resize" — verified: `pump` is
`async fn pump(&mut self)`, `resize` is a non-`async fn resize(&mut self)` whose two calls
(`Grid::resize`, `pty_process::Pty::resize`) are both synchronous. The borrow checker
makes the exclusion structural and the absence of `.await` makes the yield impossible.
This is the strongest sentence in the comment, and correctly identifies that a mechanism
which cannot fire is worse to state than none.

**One overstatement.** "the grid goes first because it is **the half that can REFUSE**"
is not exclusive. `Pty::resize` returns `Result` and `tcsetwinsize()` has four documented
failure modes (`[EBADF]`, `[EIO]`, `[ENOTTY]`, and optionally `[EINVAL]`). When it fails,
the grid has *already* adopted the new size and the PTY has not — producing precisely the
permanent, unreconciled divergence the comment offers as the argument against the reverse
order. The order chosen is still the right one, because the grid's failure is
deterministic validation while the PTY's is operational, but the asymmetry is narrower
than the comment claims. Recommend re-wording to that distinction rather than to an
exclusive "can refuse".

### The CUP emission — checked against the emitted bytes

Also asked for adversarially. **No transposition, correct base.**

ECMA-48 5th edition §8.3.21, verbatim from the Ecma PDF:

> **8.3.21 CUP - CURSOR POSITION** · Notation: (Pn1;Pn2) · Representation: `CSI Pn1;Pn2 04/08`
> · Parameter default values: Pn1 = 1; Pn2 = 1
> "CUP causes the active presentation position to be moved in the presentation component
> to the n-th **line** position according to the line progression and to the m-th
> **character** position according to the character path, where n equals the value of Pn1
> and m equals the value of Pn2."

So Pn1 is the line, Pn2 the character position, both 1-origin, final byte 04/08 = `H`.

`lib.rs:197` emits `format!("\x1b[{};{}H", y + 1, x + 1)` where `Grid::cursor()` returns
zero-based `(column, row)` — so `y` is the row and goes into Pn1, `x` the column into Pn2.
That is the specified order.

Rather than rest on reading it, the emitted bytes were observed directly by building an
out-of-tree consumer against the crate (nothing in the repository was modified): a 20×5
grid fed `"first\r\nsecond\r\nthird"` reports `cursor (col,row) = (5, 2)` and
`snapshot_vt()` ends `<ESC>[3;6H`. Pn1 = 3 → line 3 → row index 2 ✓. Pn2 = 6 → character
position 6 → column index 5 ✓.

The concern that a transposition would be invisible in most tests is well founded but
does not apply here: `a_second_client_attaches_to_the_screen_already_on_show` round-trips
through `snapshot_vt` → `restore` and compares the cursor on an asymmetric grid at an
asymmetric position. A transposed emission would send `<ESC>[6;3H` — line 6 on a 5-row
grid, clamping to row index 4, column index 2 — restoring `(2, 4)` against an expected
`(5, 2)`, which `assert_same_screen` fails on. The geometry was chosen so that the test
discriminates.

`render.rs:216`'s marker ("CUP takes a 1-based line then column, so row index 1 is line
2") and `lib.rs:215`'s CUF marker are both accurate. ECMA-48 §8.3.20 confirms
`CSI Pn 04/03`, default Pn = 1, moving rightwards by n character positions — and the test
asserts both the parameter and the omitted-parameter default, which is the half a
hand-written parser gets wrong. ECMA-48 §5.4 confirms `CSI P…P I…I F` exactly as both
markers state it.

### UAX-11 overstates its source; UAX-29 is accurate

`render.rs:102` — *"Derivation: UAX-11 — an East Asian Wide character occupies two
terminal columns."*

UAX-11 does not say that. It defines `East_Asian_Width` as a two-valued categorization
(narrow/wide) and is explicit that *"the actual display width of a glyph is given by the
font and may be further adjusted by layout."* The closest support is §5 Recommendations,
"When processing or displaying data": Wide characters *"In fixed-pitch fonts…take up one
Em of space"* against Narrow and Halfwidth at *"1/2 Em"* — a 2:1 ratio in typographic
units, from which two cells follows for a fixed-pitch grid. That inference is reasonable,
but it is an inference, and the annex carries a note pointing the other way:

> "Note: The East_Asian_Width property is not intended for use by modern terminal
> emulators without appropriate tailoring on a case-by-case basis."

Two further imprecisions: the marker names only East Asian Wide (W), while Fullwidth (F)
is 1 Em by the same recommendation and is equally covered by the spacer-cell path the
marker sits on; and it carries no section, where `SPECS.md` asks for `<ID> §<section>`
"where the spec has sections".

Not a blocker — the marker sits on the right behavior, and the code's actual act (skip
`SpacerHead`/`SpacerTail` when concatenating a row) depends on libghostty-vt's cell model,
which the marker also describes correctly. But it attributes a sentence to UAX-11 that is
not in UAX-11. Recommend `UAX-11 §5` and wording that the two-cell mapping is the
fixed-pitch consequence of the 1 Em / ½ Em recommendation, for W and F both.

`render.rs:264` — *"UAX-29 — a grapheme cluster is what a reader perceives as one
character, and ZWJ sequences join several codepoints into one"* — **accurate**. UAX-29
glosses grapheme clusters as "user-perceived characters" in its own Summary, and GB11
(`\p{Extended_Pictographic} Extend* ZWJ × \p{Extended_Pictographic}`, under "Do not break
within emoji modifier sequences or emoji zwj sequences") is exactly the rule the test's
`a` + U+1F469 + ZWJ + U+1F4BB + `b` exercises. Strictly this holds for *extended* grapheme
clusters and not the legacy profile, which the marker does not distinguish — immaterial,
since UAX-29 itself says extended clusters "should be used in implementations". Same
missing-section point as UAX-11; `§3.1`/GB11 would be precise.

### Judging the CAPTURES.md public-source path clause

> "A storage path may be named elsewhere in-tree for a capture of **public source**, and
> only while all of these hold: the repository, revision and path are already a build
> input, the license is named, and the hash — never the path — remains the citation of
> record."

**Conjunctive: yes, unambiguously.** "only while all of these hold" is explicit and admits
no reading where one condition substitutes for another. **Correctly applied to CAP-001:
yes** — `pins.env` pins the repository and a full 40-hex commit SHA, `tools/pty-toolchain.sh`
materialises that tree and `soak.rs` reads through it, MIT is named in `PROVENANCE.md`, and
every `Derivation:` marker cites the ID rather than a path.

**Narrow: less than it reads.** Two gaps, neither exercised here, both in the wording
rather than the application:

1. **"the license is named" is satisfied by naming any license, including a disqualifying
   one.** A capture of a public but AGPL-licensed source would satisfy "public source"
   (it is public) and satisfy the license condition (name it: `AGPL-3.0`), and the clause
   would then permit writing that path into the tree. Rules 1 and 2 forbid the underlying
   act, so the repository is not actually exposed — but this clause, read alone, does not
   carry the constraint that makes it safe, and the no-paths rule's first stated reason is
   not content-neutral. Recommend requiring the license to be one the project may derive
   from, not merely disclosed.

2. **"already a build input" does not require the revision to be immutable.** A build
   input pinned to a branch, a moving tag, or a semver range satisfies the literal words
   while pointing at bytes that can change — which is the no-paths rule's *own* second
   reason ("a path is not a stable identifier, so a claim resting on one can come to point
   at different bytes without saying so"). Here `GHOSTTY_COMMIT` is a full commit SHA and
   the instance is airtight. But as drafted, condition (b) either needs "pinned by a
   content-addressed revision" or is doing no work that condition (d) does not already do.

One scope observation, not a violation: `CAP-001`'s hash covers the **harness**, which is
what substantiates the two cited facts. The **corpus** the derivation consumes is a
different set of bytes and is not registered as a capture; its provenance rests on
`PROVENANCE.md` plus per-vector digests in `stream-initial.hex`, cross-checked against
`golden-frames.txt` by `the_corpus_is_the_one_that_was_vendored`. That is a sound design
and the digests are genuinely enforced — but the clause's closing paragraph ("the soak
test reads the corpus through them") extends the justification from the hashed artifact to
an unhashed one without saying so. Worth making explicit.
