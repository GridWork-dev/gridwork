## Notes

### citations — correct, verified against the specification rather than the fix note

`crates/gwk-pty/src/lib.rs:86` reads:

```
// Derivation: ECMA-48 §8.3.20 — CUF moves the active position forward by
// Pn columns, with parameter default Pn = 1.
```

Checked against ECMA-48 5th edition (June 1991) itself, obtained from the `Where` column
of the registry row that the marker cites. §8.3.20 reads verbatim:

```
8.3.20   CUF - CURSOR RIGHT
         Notation: (Pn)
         Representation: CSI Pn 04/03
         Parameter default value: Pn = 1
         CUF causes the active presentation position to be moved rightwards in the
         presentation component by n character positions if the character path is
         horizontal, or by n line positions if the character path is vertical, where n
         equals the value of Pn.
```

Both halves of the marker are what that section says. `04/03` is `0x43` = `C`, the final
byte the test actually emits. "Forward by Pn columns" is the horizontal-character-path
case, which is the one the test exercises; the marker does not claim to restate the
vertical branch and does not need to.

The behavior was verified, not assumed. `cargo test -p gwk-pty --locked --offline` passes
from this worktree: `hello\x1b[5C world` lands the cursor at column 16, and `a\x1b[Cb`
lands it at column 3 — the parameterized advance and the omitted-parameter default of 1,
which is what §8.3.20 specifies.

**What the first pass caught.** The marker originally cited `ECMA-48 §8.3.14`, which is
`CPR - ACTIVE POSITION REPORT` (`CSI Pn1;Pn2 05/02`) — a report solicited by DSR or sent
unsolicited, which moves nothing. A real spec, a real behavior, the wrong section: it
resolved in the registry and passed the gate. The prose was right throughout; only the
number was wrong.

The old marker also justified the default as "a CSI sequence with no parameter defaults
Pn to 1", which overgeneralizes — ECMA-48 sets defaults per control function, not per
sequence type, and plenty are 0 (§8.3.117 SGR is "Parameter default value: Ps = 0",
§8.3.39 ED likewise). The revised wording is scoped to CUF and matches the spec's own
line, fixing a second and quieter inaccuracy.

**Marker placement.** All VT behavior is delegated to the dependency, so the only
non-obvious terminal behavior this change asserts anywhere is in the test, and the marker
sits directly above it. Re-checked the rest of the gated set for behavior that should
carry a marker and does not: `DEFAULT_SCROLLBACK` is a retention policy no spec sets; the
zero-dimension refusal is the dependency's documented `Options` contract, not a terminal
control function; `write`'s byte-slice signature states a parser contract this crate does
not implement. No citation gap.

**Root cause fix, `CLEANROOM.md` rule 3.** The illustrative marker now reads
`§8.3.20 — CUF advances the active position by Pn, default 1`, and the block records what
the old example got wrong. I checked those historical claims too rather than accepting
them: §8.3.14 is indeed CPR, and ECMA-48 defines no cursor save/restore control function
anywhere in §8.3 — a search of the full text returns none, and DECSC/DECRC are DEC
private, so routing them to `XTERM-CTLSEQS` is the right pointer. Accuracy matters more
than usual in that block: it is what the next marker gets copied from, which is how the
wrong number reached shipped code in the first place. The same corrected example now also
appears in the gate's own error text.

### Non-gated observations

Neither of these bears on the four checks — both files are outside the gated prefixes.
Recorded because they came out of this review.

**`tools/no-network.sh` — the previous record's finding, now fixed and verified.** That
record flagged that the `sudo` fallback lost the caller's exported environment, so on a
hosted runner — the only place that fallback is reached — `GHOSTTY_SOURCE_DIR` arrived
unset and the build would try to clone ghostty inside a network-free namespace. The
rewrite hands the whole environment across NUL-separated via `env -0` and swaps `runuser`
for `setpriv`, with a canary that refuses to run if the environment did not survive and a
DNS probe that refuses if the namespace is not isolating. Tested both paths here rather
than reading them: the `unshare -rn` path and the `sudo … setpriv … env` path each
preserve an exported probe variable and `PATH`, run as the calling user rather than root,
and fail to resolve DNS.

Worth recording against my own previous note: the fix I suggested there — re-running
`eval "$(./tools/pty-toolchain.sh --env)"` inside the sandbox — was incomplete. It would
have restored the two `GHOSTTY_*` variables and left `PATH` replaced by sudo's
`secure_path`, which CI then hit as `cargo: command not found`. On a box where cargo sits
in `/usr/bin` (as it does here) that half of the failure is invisible, which is exactly
why it survived my review of it.

**`tools/leak-scan.sh` — hard-fails on an unstaged deletion.** Found while removing the
superseded record. The content scan greps the `git ls-files` list, which still names a
tracked file that has been `rm`ed but not staged, so grep emits "No such file or
directory" and the script exits 2 with "refusing to pass". Refusing on a diagnostic is
the right instinct, but this one is a routine working-tree state, not a scanner failure.
`git rm` stages the deletion and the scan is green again — so the workaround is real but
undiscoverable from the message, which reports a leak-scan problem for what is actually a
plain `rm`. Worth either skipping paths absent from the worktree or naming the fix in the
message.

**`tools/cleanroom-gate.sh` — the collation fix is correct, one typo.** `LC_ALL=C` now
pins both the digest and the displayed list, and the reproduction above confirms it makes
the subject locale-independent. Pinning the display to the same collation is the right
call: a reader who cannot see the order that was hashed cannot check the digest. Typo in
the new comment: "LOad-BEARING" should be "LOAD-BEARING".
